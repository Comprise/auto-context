# _root
Плагин Claude Code и Codex CLI на Go, который держит индексные файлы юнитов и библиотеку context/ в синхроне с кодом.

## Назначение
Документация проекта живёт в двух слоях: короткий индексный файл `<unit>/CLAUDE.md` (в Codex —
`AGENTS.md`, ключ `index_file`; оглавление, агент подгружает его лениво при работе с файлами каталога) и подробный `context/<unit>.md` (читается явно).
Плагин после каждого хода Claude замечает, что код юнита изменился, а документы нет, и просит
обновить их или подтвердить несущественность правки (`auto-context ack`). Текст документов пишет
сама сессия Claude по навыку `auto-context:auto-context-docs` (в Codex `$auto-context:auto-context-docs`); бинарник только следит и ведёт хэши.

## Устройство
- `cmd/auto-context` — единственный бинарник: подкоманды `hook <event> [--agent codex]`, `ack`, `status`, `changes`, `units`, `version`.
- `internal/hooks` — обработчики событий Claude Code и Codex: SessionStart (уведомления, оглавление корня,
  уборка state), UserPromptSubmit (снимок stat), Stop (diff снимка, auto-ack, feedback),
  PreToolUse в Claude и PermissionRequest в Codex (авто-разрешение простых вызовов `auto-context`), SessionEnd (удаление файлов сессии).
- `internal/project` — сервисный слой: открывает репозиторий (конфиг, дерево юнитов, кэш) и даёт
  хукам и CLI общие операции (статусы, ack, оглавление, сохранение кэша). `project.FindRoot` — поиск
  корня (перенесён из `config`); `project.Diagnose` — единая модель проблем: по ней строят отчёт
  `status`, предупреждения SessionStart и напоминания Stop.
- Пакеты-кирпичи: `units` (список файлов через `git ls-files` или обход со своим разбором
  `.gitignore`, эвристика юнитов, классификация путей), `hashing` (`source_hash` с кэшем по
  mtime/size), `frontmatter`, `docstate` (ok/stale/missing, состояние context-дока, ack),
  `rootindex` (секция `auto-context:units` в корневом индексном файле), `session` (снимок и журнал хода),
  `config`, `gitx` (запуск git), `fsutil` (политика путей, чтение и запись через `os.Root`, лимит размера, атомарная запись),
  `logx` (лог ошибок), `textx` (очистка текста из репозитория), `filestat` (отпечаток файла mtime+размер,
  общий лист зависимостей для `units`, `session` и `hooks`), `filelock` (короткая эксклюзивная
  блокировка файла с ограниченным ожиданием), `turn` (правила хода для Stop: что считается обновлением
  доков, когда допустим auto-ack, кому напоминать; без ввода-вывода).
- Параллельные сессии в одном дереве делят бинарный кэш хэшей `.auto-context/cache.v5.bin`: запись
  идёт под `filelock` со слиянием с тем, что уже на диске, поэтому сессии не теряют хэши друг друга.
  Файлы хода у каждой сессии свои.
- Параллельные сессии (и правки пользователя в редакторе) в одном дереве не различаются: Stop каждой сессии сравнивает всё дерево со своим снимком начала хода, поэтому правка, сделанная во время чужого хода, попадает в напоминание и auto-ack обеих. Отделить свои правки по stat нельзя; для параллельной работы нужны отдельные worktree.
- Плагин: `.claude-plugin/plugin.json` и `hooks/hooks.json` (Claude Code), `.codex-plugin/plugin.json` и `hooks/codex.json` (Codex; команды с `--agent codex`), `.agents/plugins/marketplace.json` (маркетплейс Codex: источник `local`, `./`, потому что Codex молча игнорирует github-источник из `.claude-plugin/marketplace.json`), общие навыки в `skills/`, POSIX sh-shim
  `bin/auto-context`, выбирающий бинарник `libexec/auto-context-<os>-<arch>` (в main бинарников нет).
- `.github/workflows/`: `ci.yml` (тесты на Linux/macOS/Windows, `claude plugin validate`),
  `release.yml`; обе проверяют манифесты Claude и Codex скриптом `.github/scripts/check-manifests.sh` (в релизе — на собранном дереве, с версией тега), и релиз кладёт `.codex-plugin`, `.agents` и `README.ru.md` в дерево. По тегу `vX.Y.Z[-pre]` с коммита из main: 6 бинарников, provenance, строгая
  проверка дерева плагина, ветка `release` с файлами плагина — новый коммит поверх прежнего, без
  истории main и без force-push, только к более высокой версии; затем GitHub Release; теги с `-`
  двигают ветку `release-next` вместо `release`). Тегов `dist/*` нет: `rollback.yml` берёт дерево
  из коммита `release vX.Y.Z` ветки `release`, а версию, занятую откатом, `release.yml` отвергает
  (`.github/scripts/rollback-took.sh`). Релиз прикладывает шесть бинарников и `checksums.txt` с плоскими именами (`sha256sum -c` работает в каталоге скачанных файлов).

## Инварианты и подводные камни
- Хуки всегда завершаются с кодом 0 (шим гасит даже фатальный выход Go с кодом 2, который Claude Code
  считает блокирующим); ошибки — в `.auto-context/log`, а то, что пользователь должен исправить
  (конфиг, маркеры, сломанный `.auto-context`), — в `systemMessage`/`additionalContext` SessionStart.
- Хуки активны лишь при `.auto-context/config.yaml` или `context/_root.md` в корне; иначе ничего не пишут.
- Бюджет времени хука — `context.Context` с дедлайном из таймаута `hooks/hooks.json` (`hooks/codex.json`);
  он покрывает вызовы git, обнаружение файлов и хэширование. По исходу бюджета хук прекращает работу
  и отвечает тем, что успел: юниты без хэша (заметка о нехватке времени) или сообщение о том, что
  время вышло.
- `.auto-context/` — каталог плагина: коммитится только `config.yaml` (и `.gitignore`, который плагин
  ведёт сам), остальное — локальное состояние.
- Модель угроз: проект может быть клонированным враждебным репозиторием, а хуки срабатывают сами.
  Поэтому служебные и документные пути идут через `fsutil.Resolve` (ничего вне репозитория и в
  `.git/`), чтения ограничены по размеру, git — через `gitx`, имена юнитов и summary очищаются,
  конфиг валидируется, текст из репозитория в контекст Claude не цитируется.
- Враждебный `.git/config` (архив с готовым `.git/`): git запускается только через `gitx.Run` с
  фиксированной защитой — `GIT_ALLOW_PROTOCOL=none` (ни один транспорт, в том числе `uploadpack`,
  `core.sshCommand`, `ext::`, не запускает программу), `GIT_NO_LAZY_FETCH=1`, `-c core.fsmonitor=false`,
  `log.showSignature=false` (`gpg.program` не вызывается), `GIT_CONFIG_NOSYSTEM=1`; по таймауту убивается
  вся группа процессов git, чтобы потомок не пережил хук. Чужое дерево (`core.worktree` наружу,
  `.git`-файл на другой репозиторий, bare) отвергает `gitx.WorkTreeOK`: плагин переходит на обход
  без git. Остаётся I-1: ключи, читающие файлы вне репозитория, не закрыты, наружу выходит лишь
  оракул «исключён / не исключён».
- Инвариант вывода: в stdout/stderr CLI, `additionalContext`/`systemMessage` и тексты хуков из
  репозитория попадают только имена, прошедшие `units.SafeName`, числа, фиксированные категории
  (`fsutil.Category`, `gitx.Brief`) и вывод `changes` (темы коммитов, имена файлов) после
  `textx.StripControls`. Полный текст ошибки — только в `.auto-context/log` (`logx.Errorf`).
- Схема хэша v2: `source_hash: v2:sha256:<hex>`. Вход — файлы юнита в «индексном виде» (в git-режиме
  только записи индекса, то есть неотслеживаемые файлы не считаются; в режиме обхода — все найденные);
  для `_root` — юниты индексного вида. Файл больше 32 MiB даёт сумму от размера и первого/последнего
  мебибайта (выборка). Прежний `sha256:<hex>` — «старая схема»: если он совпадает с хэшем по прежним
  правилам, юнит `ok` с нотой `old hash scheme`, иначе `stale`; `auto-context ack --upgrade`
  переводит такие доки на v2. Кэш хэшей версии 5 (`cache.v5.bin`): прежние файлы кэша игнорируются.
- Коды выхода CLI: 0 — успех/всё актуально; 1 — только `status --exit-code` при stale/missing;
  2 — неверное использование; 3 — ошибка (проект не открыть, битый конфиг, отказ `ack`, неактивный
  проект при `status --exit-code`). `status --json` и `units --json` печатают `format_version: 1`.
  Хуки по-прежнему всегда выходят с 0.
- Два алгоритма поиска корня: `project.FindRoot` (Go) и функция `active` в шиме `bin/auto-context`
  (sh). Оба идут вверх до `.git` или `.auto-context/config.yaml` и не поднимаются в `$HOME` снизу, но
  расходятся намеренно: `project.FindRoot` проверяет владельца маркера, шим — нет (ему нужен лишь ответ,
  включён ли плагин, чтобы показать сообщение об отсутствующем бинарнике; в другом случае оба
  результата безопасны). Шим сужает `PATH` для своих утилит (убирает пустые и относительные
  элементы), а бинарь получает исходный `PATH`. Менять один алгоритм — сверять с другим.
- Пределы: не более 800 000 файлов в дереве.
- Служебные файлы и правки доков пишутся атомарно (`fsutil.WriteAtomic`), кроме лога — он дописывается; пути внутри — относительные, через `/`.
- Правка индексного файла не считается обновлением доков; правка `context/<unit>.md` засчитывается, только
  если она не старше последней правки кода юнита в ходе; юнит, чьи доки и так совпадают с кодом,
  напоминания не получает. Файл кода с mtime старше начала хода (перенесённый `mv`/`cp -p`) auto-ack
  юнита в этом ходе запрещает.
- Версия плагина не хранится в main: её проставляет `release.yml` из тега. Иначе пользователи
  не получают обновлений.
- Спецификация и план: `docs/superpowers/specs/`, `docs/superpowers/plans/` — документы проектирования;
  где они расходятся с кодом, прав код и эти доки.

## Связи
Модуль Go `auto-context`; зависимости: `go.yaml.in/yaml/v3`, `github.com/bmatcuk/doublestar/v4`; во
время работы — `git` (необязательно). Сборка — `Makefile`
(`make test` — `go vet ./...` и `go test -race ./...`, на Linux как в CI: `-shuffle=on -json` через
`.github/scripts/check-skips.sh`, который падает на неожиданном skip; `make dist`).
