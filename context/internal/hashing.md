# internal/hashing
Считает source_hash юнита по списку файлов с кешем mtime/size.

## Назначение
Отпечаток исходников юнита; по нему решается, устарела ли документация. Кеш избавляет от перечитывания неизменённых файлов на каждом хуке.

## Публичный API / точки входа
- `SourceHash(ctx, root, files, extra, c)` — `sha256:<hex>` от строк `relpath\x00sum\n` по отсортированным файлам и `\x00unit\x00<extra>\n` по отсортированным extra. После конца `ctx` останавливается с его ошибкой на первом файле, которого нет в кеше (проверка перед чтением файла и при чтении каждого блока); суммы из кеша по-прежнему отдаются, посчитанные остаются в кеше.
- `NewCache`, `LoadCache(root)` → кеш и ошибка, если файл непригоден (`hash cache unusable…` / `hash cache corrupt…`); `CachePath(root)` — путь файла кеша этой версии (по нему `project.SaveCache` проверяет, что файл есть).
- `Cache.Prewarm(ctx, root, files, save, every)` — параллельно хеширует изменившиеся файлы и периодически вызывает `save`; после конца `ctx` новые файлы не начинаются, а начатые прерываются — частичный результат; `UseStats` — доверять mtime/size из `Discover`; ещё `Prune` (пустой кеш не трогает), `Save`, `Len`, `Dirty` (кеш изменён с загрузки/сохранения); `MaxHashSize` = 32 МиБ.

## Инварианты и подводные камни
- Содержимое хешируется с `\r\n` как `\n` (и на стыке чанков): чекаут с autocrlf даёт тот же отпечаток.
- Формат отпечатка записан во frontmatter всех доков: его изменение один раз делает затронутые юниты stale.
- Поля кеша закрыты: любое изменение помечает его изменённым, `Save` пишет только тогда (или если файла нет), атомарно, без fsync.
- Файл кеша — `.auto-context/cache.v5.bin` (`cache.go`): заголовок `acache 5\n`, затем записи, отсортированные по пути: `uvarint(len) путь | varint(mtime_ns) | uvarint(size) | [32]byte сумма | флаги` (бит 0 — racy, прочие биты нулевые). Сумма хранится в `Entry.Sum` сырыми 32 байтами, в hex — только в строке отпечатка. Загрузка 200 тыс. записей — около 25 мс (`BenchmarkLoadSave200k`).
- У каждой версии кеша свой файл: установки разных версий (Claude и Codex) в одном дереве не вытесняют кеши друг друга. Файлы других версий (`cache.json` версий до 4, `cache.vN.bin`) не читаются, не удаляются и не перезаписываются.
- Непригодный файл своей версии (битый — неверный заголовок, обрезанная, несортированная или повторная запись, неизвестный бит флагов, переполненный varint; больше 256 МиБ; не обычный файл) даёт пустой кеш, который перезаписывается при следующем `Save`. Файл может прийти из враждебного репозитория, поэтому путь записи должен быть чистым локальным путём через `/`: непустой, не абсолютный, без пустых сегментов, `.` и `..`, без NUL и `\`, не длиннее 64 КиБ; на Windows ещё `filepath.IsLocal`. Иначе файл считается битым.
- `Save` сливается с файлом на диске под блокировкой `cache.v5.bin.lock` (`filelock` по лексическому пути: симлинк или FIFO на месте lock-файла отвергается; ожидание не дольше 500 мс; не дождался или блокировку не взять — слияние всё равно идёт, без защиты): параллельные сессии не теряют посчитанные друг другом хэши. Запись с диска берётся, если её mtime и size совпадают с текущими (статистика `UseStats`, иначе Lstat обычного файла), а своя запись — нет или её нет вовсе. Racy-записи с диска и записи файлов вне набора последнего `Prune` не берутся. В памяти кеш слиянием не меняется.
- `UseStats`: при совпадении записи кеша со статистикой `Discover` файл не трогается; иначе `hashFile` делает Lstat и читает только обычный файл (симлинки-исходники `Discover` не отслеживает). Статистика должна быть из того `Tree`, чьи файлы хешируются в этом процессе.
- «Racily clean», как в git: если mtime файла не старше момента чтения хотя бы на 2 с (`racyMargin`: грубые mtime FAT/ext3/HFS+, расхождение часов), запись помечается `racy` — перезапись того же размера в тот же тик не изменила бы mtime и size. Такая запись служит только процессу, который её посчитал: `LoadCache` её отбрасывает, следующий запуск перехеширует (и уже сохранит обычную запись). Версия кеша `cacheVersion` = 5 (4 — файлы больше `MaxHashSize` хешируются по выборке, 5 — бинарный файл); `cmd/auto-context` печатает её в `version -v`.
- Файл больше `MaxHashSize` (32 МиБ) хешируется по выборке: `sha256("large\x00" + <размер> + "\x00" + LF(первый 1 МиБ) + LF(последний 1 МиБ))`, читается не более 2 МиБ. Ограничение: изменение в середине такого файла при том же размере и mtime не видно — тот же класс риска, что у racy-кеша; для CRLF-чекаутов размер другой.
- `LoadCache` отбрасывает racy-записи, не помечая кеш изменённым: перезапись ради этого не нужна.
- `Prewarm`: результаты идут через буферизованный канал (256), `save` выполняется в отдельной горутине и не задерживает воркеров; пока он идёт, кеш только читается, а новые результаты ждут и применяются после него.
- Совпадение mtime+size при изменённом содержимом файла, mtime которого старше хеширования больше чем на 2 с, даёт старый хеш — осознанный компромисс.
