# auto-context

[English](README.md) · **Русский**

**Плагин для [Claude Code](https://docs.claude.com/en/docs/claude-code) и
[Codex CLI](https://developers.openai.com/codex), который держит документацию проекта в синхроне с
кодом.**

Агент лучше работает с проектом, когда знает его устройство, но читать весь код на каждую задачу
дорого, а написанные когда-то доки быстро устаревают. auto-context раскладывает короткие описания
по частям проекта и следит, чтобы они не отставали от кода.

## Как это работает

Проект делится на **юниты** — каталоги с модулем (`go.mod`, `package.json`, …) или с достаточным
числом файлов кода. У каждого юнита два документа:

```
repo/
├── CLAUDE.md                 # ваши правила + оглавление юнитов (ведёт плагин)
├── services/billing/
│   └── CLAUDE.md             # назначение и ключевые файлы юнита — коротко
└── context/
    ├── _root.md              # устройство проекта целиком
    └── services/billing.md   # подробно: API, инварианты, связи
```

- `<unit>/CLAUDE.md` Claude Code подгружает сам (в Codex индексные файлы называются `AGENTS.md`,
  см. [Codex](#codex)), когда работает с файлами юнита.
- `context/<unit>.md` Claude читает, только когда нужны подробности.
- Если Claude изменил код юнита, а доки остались прежними, в конце хода плагин напомнит обновить
  их или подтвердить, что правка несущественна.
- Изменения, сделанные между сессиями (`git pull`, ручные правки), плагин покажет при старте.
- Оглавление юнитов в корневом индексном файле лежит между строками `<!-- auto-context:units -->` и
  `<!-- /auto-context:units -->`. Строку заголовка сразу после открывающего маркера можно перевести или заменить;
  сам список плагин переписывает. Если маркеры сломаны (нет одного, лишний или они идут не в том порядке), оглавление
  не обновляется, а `auto-context status` предупреждает об этом: поправьте маркеры вручную.

Когда доки актуальны, плагин молчит и не тратит контекст (единственное исключение — однострочная заметка о языке
доков, если задан `language`).

## Требования

- Claude Code 2.1.304 или новее (CLI, расширение для IDE или desktop-приложение; более старые версии не проверялись) или Codex CLI.
- Linux, macOS или Windows (amd64 или arm64). Go не нужен: плагин ставится с готовыми бинарниками.
- `git` — желательно, но не обязательно.
- **Windows:** нужен [Git for Windows](https://git-scm.com/downloads/win) — без Git Bash хуки плагина
  не запускаются. Если Git Bash стоит не в стандартном месте, укажите путь в `settings.json`:

  ```json
  { "env": { "CLAUDE_CODE_GIT_BASH_PATH": "C:\\Program Files\\Git\\bin\\bash.exe" } }
  ```

- **Codex:** только Linux и macOS (в Windows — внутри WSL). Хуки Codex — команды POSIX sh; как Codex запускает их в Windows без WSL, не проверено.

## Установка

В Claude Code:

```
/plugin marketplace add Comprise/auto-context
/plugin install auto-context@auto-context
```

Без SSH-ключа для GitHub задайте перед этим `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1`.

Об обновлении — в разделе [Обновление](#обновление) (автообновление сторонних маркетплейсов по умолчанию выключено).

## Обновление

- **Claude Code:** `claude plugin update auto-context@auto-context` или автообновление в `/plugin` → Marketplaces.
  Затем перезапустите Claude Code: новая версия подхватится следующей сессией.
- **Codex:** обновите маркетплейс `auto-context` и плагин из `/plugins` (точная команда CLI для обновления маркетплейса
  зависит от версии Codex, см. `codex plugin marketplace --help`), затем снова доверьте хукам плагина в `/hooks`
  и начните новую сессию: после обновления Codex просит доверие заново, а недоверенные хуки не запускаются.
- В проекте работает один бинарник за раз, поэтому не смешивайте версии в одном репозитории: формат доков на диске
  меняется между релизами (см. `CHANGELOG.md`). Проекту, написанному v1.0.0, после обновления нужен один раз
  `auto-context ack --upgrade` (см. [CI](#ci)).
- **Закрепление версии.** Каждый релиз помечен ещё и тегом `dist/vX.Y.Z` в ветке `release`. Для Codex:
  `codex plugin marketplace add Comprise/auto-context --ref dist/vX.Y.Z`. Принимает ли `/plugin marketplace add`
  Claude Code ref для GitHub-источника, зависит от его версии; смотрите справку `/plugin` — здесь это не проверялось.
  Теги `dist/` появятся с первым релизом, который их публикует. Пре-релизные теги двигают вместо этого ветку
  `release-next`, которую тестеры могут поставить через `--ref release-next`.

## Удаление и отключение

- **Удалить плагин:** в Claude Code — `/plugin uninstall auto-context@auto-context`; в Codex — удалите его в
  `/plugins` и уберите маркетплейс командой `codex plugin marketplace remove auto-context`. Эти команды здесь не
  проверялись; если они не подходят, смотрите справку `/plugin` и `codex plugin marketplace --help`.
- **Отключить только в одном проекте:** хуки работают, пока в проекте есть `.auto-context/config.yaml` или
  `context/_root.md`. Удалите оба файла (и каталог `.auto-context/`) — плагин замолчит и ничего там не запишет.
  Созданные доки (`CLAUDE.md`, `context/`) останутся обычными файлами; секцию между
  `<!-- auto-context:units -->` и `<!-- /auto-context:units -->` в корневом индексном файле удалите, если она не нужна.

## Проверка

Бинарники собирает release-workflow, происхождение сборки аттестовано. Чтобы проверить установленный бинарник
(путь зависит от того, где агент хранит плагины; для Claude Code это обычно каталог
`~/.claude/plugins/cache/`):

```sh
gh attestation verify <plugin dir>/libexec/auto-context-linux-amd64 -R Comprise/auto-context
(cd <plugin dir> && sha256sum -c checksums.txt)
```

`checksums.txt` в дереве релиза перечисляет бинарники путями `libexec/...`, поэтому его проверяют из каталога
плагина, как выше. В GitHub Release лежат ещё архив `auto-context-vX.Y.Z.tar.gz` и свой `checksums.txt` с плоскими
именами файлов; его проверяйте в каталоге, куда скачали файлы. Архив и оба файла сумм тоже аттестованы. Они
появляются начиная с первого релиза, собранного обновлённым workflow; у более старых их нет. В macOS используйте
`shasum -a 256 -c checksums.txt`.

## Codex

Codex поддерживается в Linux и macOS (в Windows — через WSL).

Хуки и навыки те же, но индексные файлы юнитов называются `AGENTS.md`, а навыки вызываются через `$`.

```
codex plugin marketplace add Comprise/auto-context --ref release
```

Затем в Codex:

1. `/plugins` → установите `auto-context`.
2. `/hooks` → доверьте хукам плагина. После обновления плагина Codex может спросить доверие снова. Хуки работают только в сессии, начатой после доверия.
3. Начните новую сессию и выполните `$auto-context:init` (не встроенный `/init` Codex). Навык сам запишет
   `index_file: AGENTS.md` в `.auto-context/config.yaml` до создания документов.

Остальные навыки: `$auto-context:sync`, `$auto-context:status`. Напоминания в конце хода приходят как обычное продолжение
хода.

В Codex `auto-context` не в PATH: хуки предлагают команды с абсолютным путём
(`${CODEX_HOME:-~/.codex}/plugins/cache/<marketplace>/auto-context/<version>/bin/auto-context ack …`; путь с пробелами
или другими необычными символами — в одинарных кавычках), и навыки выполняют их так же; если хук пути
не дал, навык ищет только в маркетплейсе `auto-context` кэша плагинов Codex
(`${CODEX_HOME:-~/.codex}/plugins/cache/auto-context/auto-context/<version>/bin/auto-context`, старшая версия), показывает
вам путь перед первым запуском и всегда запускает его в кавычках; если не нашёл — спрашивает вас. Бинарник плагина по абсолютному пути обычно запускается без запроса; если
Codex всё же собрался спросить, хук `PermissionRequest` одобряет вызовы CLI плагина только по этому абсолютному пути (`ack`,
`status`, `units`, `changes`, `version`; `ack --exclude` всегда спрашивает).

Маркетплейс для Codex описан в `.agents/plugins/marketplace.json` ветки `release`
(источник `local`, `./`); идентификатор плагина — `auto-context@auto-context`.

## Быстрый старт

Плагин ставится глобально, но работает только в проектах, где его включили. Откройте проект в
Claude Code и выполните (в Codex — `$auto-context:init`, см. [Codex](#codex)):

```
/auto-context:init
```

Claude найдёт юниты, покажет список на подтверждение, спросит язык документов и напишет их.
Созданные `CLAUDE.md`, `context/`, `.auto-context/config.yaml` и `.auto-context/.gitignore`
(плагин создаёт его, чтобы логи и кэши не попадали в git) закоммитьте — так документы получат и коллеги.

## Как пользоваться

**Работайте как обычно.** Просите Claude менять код — о документах думать не нужно.

**Если Claude изменил код, а доки нет,** в конце ответа плагин напомнит ему об этом, и Claude сам
решит: обновить `context/<unit>.md` (если изменилось назначение, API, структура или важное
поведение) или подтвердить, что правка мелкая (`auto-context ack`). Если документы обновлены в том
же ходе, плагин подтверждает их сам. Напоминание приходит не чаще раза на юнит за ход.

**После `git pull`, смены ветки или правок вне Claude** при старте сессии плагин сообщит, какие
документы устарели. Чтобы обновить их сразу:

```
/auto-context:sync
```

**Появился новый модуль или каталог с кодом** — плагин заметит его, и Claude спросит, описывать ли
его или не считать отдельным юнитом. **Каталог удалён** — его документы плагин покажет как лишние,
а Claude удалит их, только спросив вас.

**Проверить, всё ли актуально,** — `/auto-context:status`.

**Хотите вести документы на одном языке** — задайте `language` в настройках (`/auto-context:init`
спрашивает его сам).

## Команды

| Команда (Claude Code / Codex) | Что делает |
|---|---|
| `/auto-context:init` / `$auto-context:init` | включить плагин в проекте и написать документы |
| `/auto-context:sync` / `$auto-context:sync` | найти устаревшие документы и обновить их |
| `/auto-context:status` / `$auto-context:status` | показать, какие документы устарели, ничего не меняя |

Claude пользуется и консольной утилитой — её можно запускать вручную:

| Команда | Что делает |
|---|---|
| `auto-context status` | состояние документов юнитов: `ok`, `stale`, `missing` |
| `auto-context status --stale` | только устаревшие и недостающие |
| `auto-context status --exit-code` | код 1, если есть stale/missing — для CI |
| `auto-context status --json` | то же в JSON; сочетается с `--stale` и `--exit-code` |
| `auto-context units` | список юнитов |
| `auto-context units --json` | то же в JSON |
| `auto-context ack <unit…>` | правка несущественна: считать документы актуальными |
| `auto-context ack .` | то же для корня проекта (`_root`, `context/_root.md`) |
| `auto-context ack --upgrade` | переписать доки, актуальные по старой схеме хэша, на схему v2 |
| `auto-context ack --exclude <unit>` | не считать каталог отдельным юнитом (`_root` исключить нельзя) |
| `auto-context changes <unit>` | что изменилось в юните с последнего обновления доков |
| `auto-context version` | версия плагина |
| `auto-context version -v` | ещё ревизия, версия Go, платформа и версии форматов на диске (для сообщений об ошибках) |

**Коды выхода.** 0 — успех или всё актуально; 1 — только `status --exit-code`, если есть stale или missing;
2 — неверное использование; 3 — ошибка (проект не открыть, битый конфиг, отказ `ack`, либо проект не включён,
а запрошен `status --exit-code`). В CI 1 значит устаревшие доки, а 3 — сломанную настройку: различайте их.

**Вывод.** `status` печатает таблицу с колонками `UNIT STATE DOC`; у состояния может быть пометка в скобках,
например `stale (…)`, а следом идут строки `warning:` и `note:` — всё в stdout. С `--json`
(`format_version` 1) документ такой: `{"format_version":1,"paused":…,"units":[{"unit","state","doc","note","detail"}],"orphans":{"shown":[…],"hidden":N},"warnings":[…],"notes":[…]}`.
`units` печатает по строке на юнит через табуляцию: `path`, `reason` (`root`, `include`, `module` или `files`) и
число файлов; с `--json` это `{"format_version":1,"units":[{"path","reason","files"}]}`. Остальные команды
пишут ошибки в stderr.

## Настройка

Настройки необязательны и лежат в `.auto-context/config.yaml`. Значения по умолчанию:

```yaml
min_files: 5            # сколько файлов кода делает каталог юнитом
include: []             # каталоги, которые всегда юниты
exclude: [vendor/**, node_modules/**, "**/testdata/**", dist/**, build/**]
track: []               # файлы без кодового расширения, которые тоже считать кодом юнита
index_file: CLAUDE.md   # имя индексного файла юнитов: CLAUDE.md или AGENTS.md (Codex)
language: ""            # язык документов: ru, en, pt-BR…; пусто — как в существующих доках
max_session_notice: 10  # сколько юнитов перечислять в напоминании при старте (0 — только числа)
code_extensions: [.go, .ts, .tsx, .mts, .cts, .js, .jsx, .mjs, .cjs, .vue, .svelte, .py, .rs, .java, .kt,
                  .scala, .swift, .dart, .rb, .php, .cs, .fs, .c, .h, .cc, .cpp, .cxx, .hh, .hpp, .m, .mm,
                  .ex, .exs, .erl, .hs, .clj, .lua, .zig, .sh, .sql, .proto, .graphql, .tf]
module_markers: [go.mod, package.json, Cargo.toml, pyproject.toml, pom.xml, build.gradle]
```

- Заданный список заменяет значение по умолчанию, а не дополняет его.
- Чтобы каталог не был отдельным юнитом, добавьте его в `exclude` (или `auto-context ack --exclude`);
  чтобы плагин его вообще не видел — `<dir>/**`.
- `include`, `exclude` и `track` — glob-шаблоны относительно корня репозитория (синтаксис `doublestar`, а не
  просто имена каталогов): каждый до 256 байт и 8 групп `{}`. `min_files` не меньше 1, `max_session_notice` — 0..100.
  Список без годных элементов заменяется значением по умолчанию; явный `[]` остаётся пустым.
- Файлы, которые игнорирует git (`.gitignore`), при поиске юнитов не учитываются, но уже закоммиченный файл
  учитывается, даже если подпадает под `.gitignore`. Неотслеживаемые неигнорируемые файлы идут в счёт `min_files`
  (влияние на хэши — в разделе [CI](#ci)).
- Ошибочная настройка отбрасывается с предупреждением, остальные продолжают действовать. Конфиг целиком ломают
  (отслеживание доков приостанавливается, пока его не исправят): синтаксическая ошибка YAML; нечитаемый файл,
  файл больше 1 МиБ или не обычный файл; повторный или не строковый `index_file`; `index_file` кроме `CLAUDE.md`
  и `AGENTS.md`. Пока конфиг сломан, `ack`, `units` и `changes` отказываются работать.

## CI

`auto-context status --exit-code` можно сделать проверкой для pull request. Начиная со схемы хэша v2 `source_hash`
считается только по файлам, которые отслеживает git (индекс), поэтому неотслеживаемые файлы, `.git/info/exclude`
и глобальный `core.excludesFile` его не меняют: хэш в вашей рабочей копии равен хэшу в чистом клоне. Файлы больше
32 МиБ хэшируются по размеру и первому и последнему мебибайту.

- Выполните `auto-context ack` (или обновите доки) и закоммитьте доки вместе с кодом — тогда CI увидит `ok`.
- Запускайте проверку в чистом checkout коммита, с установленным `git` и полным деревом.
- Код 1 — устаревшие или недостающие доки, 3 — ошибка настройки (см. [Команды](#команды)).
- Доки, написанные v1.0.0, несут хэши `sha256:`. Пока ничего не менялось, они показываются как `ok` с пометкой
  `old hash scheme`; один раз выполните `auto-context ack --upgrade` и закоммитьте результат. Юниты, чей старый хэш
  воспроизвести нельзя (например, с файлом больше 32 МиБ), становятся `stale` и требуют обычного `ack`.

## Если что-то не работает

- `auto-context status` покажет предупреждения: о конфиге, `.gitignore`, git.
- В `/hooks` должны быть хуки плагина: `SessionStart`, `UserPromptSubmit`, `Stop`, `PreToolUse`,
  `SessionEnd` (в Codex вместо `PreToolUse` — `PermissionRequest`, и хуки нужно доверить).
- В Codex хук `SessionEnd` при выходе из TUI не срабатывает (сессию держит фоновый app-server), поэтому файлы сессии в `.auto-context/state` остаются; SessionStart удаляет те, что старше 7 дней.
- Две сессии агента в одном каталоге видят правки друг друга: напоминание или auto-ack может прийти не той сессии. Для параллельной работы используйте отдельные `git worktree`.
- Ошибки плагина пишутся в `.auto-context/log`. Работу агента плагин не прерывает никогда.
- Репозиторий в сотни тысяч файлов может не уложиться в бюджет времени хука. Больше 800000 файлов плагин
  перечислять отказывается; добавьте большие сгенерированные каталоги в `.gitignore`, а для большого рабочего дерева
  выполните `git config core.untrackedCache true`, чтобы ускорить список файлов плагина (`git ls-files`).
  Для собственных вызовов git плагин всегда выключает `core.fsmonitor`.
- Если каждый хук сообщает о таймауте git, проверьте, что `.gitignore` и `.git/info/exclude` — обычные файлы: FIFO
  или устройство на их месте заставляет git зависнуть на чтении. Обход дерева вместо git в этом случае не включается.
- Сообщая об ошибке, приложите вывод `auto-context version -v`, `auto-context status` и хвост
  `.auto-context/log`.

## Безопасность

Плагин рассчитан на то, что репозиторий может оказаться чужим. Что он гарантирует:

- Собственные чтение и запись файлов плагина остаются внутри репозитория: симлинки наружу, в `.git/` и в каталог
  состояния отклоняются, симлинк-док должен указывать на другой `.md`-файл, а файлы, не являющиеся обычными, не читаются.
- Ничто из `.auto-context/config.yaml` не исполняется.
- Текст конфига (кроме проверенного кода `language`), лога и stderr git не попадает ни к агенту, ни в терминал: в сообщениях только имена юнитов,
  прошедшие проверку безопасности, числа и фиксированные категории. Полный текст ошибок — только в
  `.auto-context/log`.
- git запускается с защитой: без пейджера, fsmonitor, запросов, сетевых транспортов, догрузки объектов и системного
  конфига. Список файлов (`git ls-files`) и `auto-context changes` запускаются только после проверки, что рабочее
  дерево — то, на которое указывает репозиторий; вызовы `check-ignore` и `rev-parse` идут без этой проверки.

Что он не гарантирует и что нужно считать недоверенными данными:

- Сами доки, вывод `auto-context changes` (темы коммитов, имена файлов, строки `git status`) и имена каталогов-юнитов —
  это текст из репозитория, и он попадает к агенту. Управляющие символы вырезаются, но содержимое не проверяется:
  в нём могут быть инструкции, рассчитанные на модель.
- Сам git читает `.git/config` репозитория и несколько файлов вне него (`core.excludesFile`, `include.path`,
  alternates). Не открывайте с включённым плагином репозиторий, полученный архивом вместе с каталогом `.git/`,
  если ему не доверяете.
- О уязвимостях сообщайте через приватный GitHub security advisory (см. `SECURITY.md`).

## Разработка

```sh
make test                                   # go vet + go test (нужны Go 1.27 и git)
make dist                                   # бинарники для 6 платформ в libexec/
claude --plugin-dir /path/to/auto-context   # запустить Claude Code с локальной версией (после make dist)
```

`claude --plugin-dir` работает только после `make dist`: шим ищет бинарники в `libexec/`, которого нет в `main`.
Чтобы проверить плагин в Codex локально, после `make dist` добавьте каталог как маркетплейс командой
`codex plugin marketplace add <path>`.

Релиз — тег `vX.Y.Z` на коммите из `main`, и ветка `release` двигается только на более высокую версию: workflow
соберёт бинарники и обновит ветку `release`, из которой ставится плагин. Пре-релизные теги (`vX.Y.Z-pre`) ветку
`release` не трогают. Версия берётся из тега. Устройство кода описано в [`context/_root.md`](context/_root.md).
