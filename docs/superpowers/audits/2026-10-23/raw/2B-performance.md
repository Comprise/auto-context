## Находки

### P-M1. Stop без изменений кода загружает и прореживает весь кэш хэшей
**Severity: Medium**
**Где:** `internal/hooks/stop.go:66-70`, `internal/project/project.go:203-205`, `internal/hooks/stop.go:78`, затем `project.go:336`.

Stop собирает `files` из `j.CodeChanged`. Если код не менялся, список пуст. Но `p.Prewarm(files)` всё равно вызывает `p.Cache()`, а тот делает `hashing.LoadCache`: читает 27,7 МБ JSON и выделяет около 54 МБ. Затем `SaveCache` вызывает `Prune(p.tree.Tracked())`: клон списка из 208k путей и map на 208k ключей.

**Влияние (замер, rb):** около 130 мс CPU из ~520 мс wall, то есть ~25% каждого «пустого» Stop. Stop срабатывает на каждом ходе агента, и большинство ходов код не трогает.

**Рекомендация:**
```go
// project.go
func (p *Project) Prewarm(files []string) {
	if len(files) == 0 {
		return // nothing to hash: do not load the cache
	}
	p.Cache().Prewarm(p.root, files, func() { _ = p.SaveCache() }, cacheSaveEvery)
}
```
`SaveCache` уже ничего не делает при `p.cache == nil`. `Prune` стоит вызывать только если кэш грязный (`c.dirty`), иначе его O(N) тратится зря:
```go
func (c *Cache) Prune(tracked []string) { if c.Len() == 0 { return } ... }
// и в SaveCache: if !p.cache.Dirty() && cacheFileExists { return nil }
```

### P-M2. После правки context-дока каждый следующий Stop этого хода заново строит статусы всех юнитов
**Severity: Medium**
**Где:** `internal/hooks/stop.go:139` и `:290-295` (`fresh` берётся из накопленного `j.DocsTouched`), `stop.go:64`, `internal/project/project.go:270-275`.

`recordTurn` возвращает кандидатов на auto-ack из **всего** `j.DocsTouched` за ход, а не из диффа этого Stop. `AckTouched` при `len(touched) > 0` безусловно вызывает `RefreshIndex()`, то есть `Statuses()`: читает все N context-доков, разбирает их YAML, хэширует все юниты (из кэша) и перестраивает корневой индекс. Сам повторный ack идемпотентен, а полный пересчёт — нет.

**Влияние (замер, rb, 8k юнитов):** Stop без новых изменений после одной правки дока занимает 0,78 с против 0,51 с, maxrss 411 МБ против 222 МБ. Цена повторяется на каждом Stop до конца хода. В профиле `AckTouched` занимает 39% CPU, из них `RefreshIndex` и `Statuses` — 26%.

**Рекомендация:** передавать в auto-ack только юниты, чей context-док изменился в диффе **этого** Stop (или чей ack сейчас реально записал хэш), и обновлять индекс только при фактической записи.
```go
// recordTurn: собрать docsNow := map[unit]bool из текущего Diff
for _, u := range j.DocsTouched {
	if !docsNow[u] && !codeNow[u] { continue } // ничего нового с прошлого Stop
	...
}
// AckTouched: refresh index only if something was written
wrote := false
... if changed { wrote = true }
if wrote || summaryMayHaveChanged { indexErr = p.RefreshIndex() }
```
`docstate.Ack` для этого должен возвращать `(written bool, err error)`.

### P-M3. Корневой индекс строится через полный `Statuses()` с хэшированием всех юнитов, хотя нужны только summary
**Severity: Medium**
**Где:** `internal/project/project.go:297-300` (`RefreshIndex`), `:213-226` (`Statuses`), `internal/docstate/docstate.go:65-95`.

`UpdateIndex` использует только `Unit` и `Summary`. Но `RefreshIndex` вызывает `Statuses()`, а тот делает Prewarm всех файлов и `SourceHash` каждого юнита. Этот путь проходят auto-ack в Stop, `ack` CLI и `ack --exclude`. В `ack --exclude` вдобавок выполняется второй полный `project.Open` (`main.go:297`).

**Влияние:** на rb `Statuses` занимает около 0,25 с CPU на каждый вызов. Из них около 0,1 с — `frontmatter.Read` на 8k доков, остальное — хэши из кэша и `Prewarm` по 200k путей. При холодном кэше `ack` одного юнита хэширует весь репозиторий.

**Рекомендация:** отдельный дешёвый путь для индекса:
```go
// docstate
func SummaryOf(root, unit string) string { _, body, err := frontmatter.Read(...); ...; return frontmatter.Summary(body) }
// project
func (p *Project) RefreshIndex() error {
	entries := make([]rootindex.Entry, 0, len(units))
	for _, u := range p.tree.Units() { entries = append(entries, rootindex.Entry{Unit: u.Path, Summary: docstate.SummaryOf(p.root, u.Path)}) }
	return rootindex.Update(...)
}
```
Ещё лучше точечно обновлять строки только у затронутых юнитов: распарсить текущую секцию, заменить summary у изменённых юнитов, добавить или удалить юниты по дереву.

### P-M4. Кэш хэшей — монолитный JSON: целиком читается и целиком перезаписывается при любом изменении, racy-записи добавляют лишние перезаписи
**Severity: Medium**
**Где:** `internal/hashing/hashing.go:68-97` (`LoadCache`, удаление racy → `dirty`), `:122-141` (`Save`), формат `Entry` (hex-строка 64 Б плюс JSON-ключи).

- Размер около 138 Б на запись: 27,7 МБ на 200k файлов. `maxCache = 256 MiB` допускает около 1,8 млн записей, то есть файл около 250 МБ.
- Правка одного файла делает кэш грязным, и `Save` маршалит и пишет весь файл: 130–150 мс CPU на rb.
- Racy-запись сохраняется, при следующей загрузке выкидывается, ставится `dirty=true` — ещё одна полная перезапись. Получается минимум две полные перезаписи на каждую правку, сделанную агентом прямо перед Stop.
- Параллельные сессии перезаписывают файл целиком по принципу «побеждает последний», и работа холодного хэширования одной сессии может пропасть (см. P-L6).

**Влияние (замер):** `LoadCache` 120–140 мс плюс `Save` 130–150 мс на rb. Это ~25–50% CPU у Stop с правками кода. Аллокации при загрузке — 54 МБ (вместе с P-L1).

**Рекомендация:** компактный бинарный формат, сумма в сыром виде:
```go
// header "acache 4\n", then sorted records:
// uvarint(len(path)) path | varint(mtime) | uvarint(size) | [32]byte sum | flags
```
Это около 60–70 Б на запись при пути ~25 Б, разбор без reflection, быстрее примерно в 5–10 раз. Если оставлять JSON, нужно хотя бы:
- хранить сумму как `[32]byte` в base64 или в бинарном виде;
- не ставить `dirty` только из-за выброшенных racy-записей: файл перепишется, когда их перехэшируют;
- при значительном размере шардировать по юниту (`cache/<sha(unit)[:2]>.bin`): Stop тогда читает и пишет только шарды изменённых юнитов, и стоимость становится O(изменённое), а не O(репозиторий).

### P-M5. Память: около 570 Б живой кучи на файл, GOGC=400 и жёсткий лимит 512 МиБ — первым ломается лимит памяти, а не таймаут
**Severity: Medium**
**Где:** `cmd/auto-context/main.go:173-174`. Копии данных:
- `units/gitfiles.go:59-67` — `res.Out` плюс строки путей;
- `walk.go:96-101` — `kept`;
- `walk.go:331-333` — `tracked` и `stats`;
- `units.go` `Stats()` — `maps.Clone`;
- `session.LoadSnapshot` — второй map;
- кэш хэшей — третий map;
- `Tracked()` — клоны в `Prune` и `Orphans`.

**Замер (rb, 200k):**

| Сценарий | maxrss |
|---|---|
| Stop с auto-ack | 428 МБ |
| Stop с рехэшем всего дерева | 529 МБ |
| session-start без кэша | 427 МБ |

Живая куча около 114 МБ, при GOGC=400 цель доходит до 383 МБ.

Если экстраполировать линейно, живая куча превысит 512 МиБ примерно на 0,9 млн файлов. При этом `maxList` (256 МиБ листинга) и `maxCache` допускают около 1,8–2 млн. Между этими значениями рантайм непрерывно запускает GC, отдавая на него до ~50% CPU, и все хуки замедляются в разы. На машинах с малым объёмом RAM пики в 400–530 МБ на каждом ходу тоже заметны.

**Рекомендация:**
1. Согласовать пределы: либо поднимать `SetMemoryLimit` по размеру листинга (например, `max(512MiB, 1.5KiB*len(files))`), либо снизить `maxList` до реально поддерживаемого объёма (~600k путей) и отказывать с понятной ошибкой.
2. Убрать лишние копии:
   - `Snapshot` строить из `t.stats` без `maps.Clone`: дерево дальше не используется, достаточно метода `TakeStats()`, который передаёт map;
   - `Prune` делать по `t.stats` (map уже есть), а не через `Tracked()` и новый map;
   - не хранить одновременно `files` и `kept`: фильтровать на месте (`kept := files[:0]`).
3. Для Stop: сохранять снимок отсортированным и сравнивать потоково с отсортированным `tracked` (merge-diff), тогда второй map на N записей не нужен.
4. GOGC 400 оставить, но включать только когда листинг меньше ~100k; для больших репозиториев хватит 100–200.

### P-M6. Хэширование без ограничения размера файла
**Severity: Medium** (производительность; во враждебном репозитории ещё и DoS)
**Где:** `internal/hashing/hashing.go:197-230` (`hashFile`), вызовы из `Prewarm` и `fileSum`.

Любой файл с кодовым расширением хэшируется целиком при каждом изменении mtime или size, и ещё раз, если хэш racy. В списке расширений есть `.sql`, `.js`, `.proto`, `.tf`, а значит дампы БД, минифицированные бандлы и сгенерированный код.

**Замер:** один разреженный файл `dump.sql` на 4 ГБ даёт 2,6 с на каждый `status` или Stop, который его перехэширует, и два рехэша подряд в racy-окне. Десяток таких файлов в разных юнитах выводит SessionStart за 60 с. Прогресс сохраняется раз в 5 с, так что в итоге всё досчитается, но хуки при этом гибнут по таймауту.

**Рекомендация:** порог (например, 32 МиБ). Выше порога хэшировать «размер + первые и последние 1 МиБ», с отдельным маркером в сумме, или исключать файл с предупреждением discovery:
```go
const maxHashSize = 32 << 20
if fi.Size() > maxHashSize {
	// sample head+tail; a change in the middle with same size+mtime is the same risk class as racy-clean
	h.Write([]byte("large\x00")); binary.Write(h, binary.LE, fi.Size())
	io.CopyN(lf, f, 1<<20); f.Seek(-1<<20, io.SeekEnd); io.Copy(lf, f)
}
```
Кроме того, хэширование стоит прерывать по дедлайну хука, связанному с hookBudget. Это пересекается с уже известной находкой «дедлайн только для git».

### P-L1. `readRegular` читает через `io.ReadAll` с удвоением буфера, хотя размер известен
**Severity: Low**
**Где:** `internal/fsutil/fsutil.go:226`.

**Замер:** при загрузке cache.json (27,7 МБ) и снимка (9 МБ) `io.ReadAll` выделяет 75,7 МБ — 22% всех аллокаций Stop. Пиковая память вдвое выше нужной, лишние копирования.

**Рекомендация:**
```go
buf := make([]byte, 0, fi.Size()+512) // a file may grow between Stat and Read
data, err := io.ReadAll(io.LimitReader(f, limit+1)) // ->
var b bytes.Buffer; b.Grow(int(fi.Size())+512); _, err = b.ReadFrom(io.LimitReader(f, limit+1)); data := b.Bytes()
```

### P-L2. `Statuses()` прогревает (хэширует) файлы юнитов, чей док missing, без frontmatter или неиспользуем
**Severity: Low**
**Где:** `internal/project/project.go:213-226`.

`Prewarm` получает файлы всех юнитов до того, как известно, нужен ли хэш. `StatusOf` хэширует только юниты с валидным frontmatter. На свежем `/auto-context:init` большого репозитория, где доков ещё нет, первый SessionStart или `status` читает и хэширует весь репозиторий впустую.

**Замер:** на rg без единого дока `status` прочитал и захэшировал 50k файлов (1,5 с CPU) и записал cache.json на 6,9 МБ. На rb то же стоило 5,7 с wall и 7,7 с CPU.

**Рекомендация:** сначала прочитать frontmatter всех доков (это дёшево), затем прогреть только юниты с `DocPresent` и разобранным хэшем:
```go
metas := make(map[string]bool)
for _, u := range units { if hasOurFrontmatter(u) { metas[u.Path] = true; files = append(files, p.tree.Files(u.Path)...) } }
p.Prewarm(files)
```
Это заодно убирает повторное чтение доков: результат `frontmatter.Read` можно передать в `StatusOf`.

### P-L3. В режиме без git lstat идёт последовательно, а в git-режиме параллельно
**Severity: Low**
**Где:** `internal/units/walk.go:399` и `:424` (`t.addFile(..., d.Info)` внутри `WalkDir`), для сравнения `parallelLstat` в `walk.go:283-313`.

**Замер:** на одном и том же дереве rb `prompt-submit` без git занимает 1,34 с, с git 0,96 с. CPU одинаковый (~1,06 с), разница — в последовательном ожидании syscall. На медленных ФС (macOS APFS, сетевые и FUSE) разница будет кратной, потому что в git-режиме lstat идёт в 8 потоков.

**Рекомендация:** при обходе собирать кандидатов (`interesting(rel)` и не ignored) в срез, а после `WalkDir` вызвать `parallelLstat(root, cands, alwaysTrue)` и `addFile(..., checked=true, ...)`, как в git-ветке.

### P-L4. CLI-команды загружают кэш хэшей, даже если он не нужен
**Severity: Low**
**Где:** `cmd/auto-context/main.go:246` (`loadRepo` → `p.CacheErr()` → `LoadCache`).

`units`, `changes`, `ack --exclude` и `ack` юнита, у которого кэш не нужен, всегда разбирают cache.json. `changes` к тому же автоматически разрешается PreToolUse и вызывается агентом часто.

**Замер:** на rb `units` с cache.json занимает 1,47 с, без него 1,07 с (под нагрузкой); по микробенчмарку разница около 130 мс CPU и +45 МБ RSS.

**Рекомендация:** предупреждение о кэше печатать только в `status`; в `loadRepo` кэш не трогать.

### P-L5. Периодическое сохранение в `Prewarm` останавливает воркеры и каждый раз пишет весь кэш
**Severity: Low**
**Где:** `internal/hashing/hashing.go:285-294`.

`save()` вызывается в горутине, которая собирает результаты, а канал `results` небуферизован. Пока идёт маршалинг всего кэша (на 1,8 млн записей это около 1–1,5 с, если экстраполировать 140 мс на 200k), все 8 воркеров стоят. Сохранение каждые 5 с даёт до ~25% накладных расходов холодного прогрева на очень больших репозиториях.

**Рекомендация:** буферизованный `results` (`make(chan result, 256)`) и сохранение в отдельной горутине по копии изменённых записей. Ещё лучше — дописываемый журнал записей, который сливается с основным файлом при `Save` (см. P-M4).

### P-L6. Параллельные сессии перезаписывают cache.json целиком
**Severity: Low**
**Где:** `internal/hashing/hashing.go:122-141`, документировано в `context/_root.md`.

Две сессии в одном дереве: каждая загружает кэш, хэширует своё и записывает весь файл. Побеждает последняя запись, хэши, посчитанные другой сессией, теряются и считаются заново. Корректность от этого не страдает, кэш восстановим. При холодном старте двух сессий на большом репозитории работа удваивается, и каждый Stop пишет около 28 МБ.

**Рекомендация:** при `Save` под `flock` (в `logx/lock_flock.go` уже есть примитивы) перечитать файл и слить записи: взять запись, у которой `MtimeNs` и `Size` совпадают с текущим stat. Либо шардирование из P-M4, которое делает конфликты редкими.

### P-L7. `git ls-files -co` на каждом хуке обходит неотслеживаемые каталоги
**Severity: Low / Info**
**Где:** `internal/units/gitfiles.go:29`.

Флаг `-o` заставляет git читать все каталоги и применять exclude. На rb это около 220 мс, ~25% времени `prompt-submit`, и столько же на каждом Stop и SessionStart.

**Рекомендация:** код менять не обязательно. В README для больших репозиториев стоит советовать `git config core.untrackedCache true` и `core.fsmonitor true`. Хуки можно запускать с `-c core.untrackedCache=true`: эта настройка лишь разрешает git использовать расширение индекса, безопасна и в список опасных ключей gitx не входит.

### P-I1. Размер файлов сессии
**Severity: Info**
**Где:** `internal/session/session.go` (`Save`, `RemoveStale`).

Снимок занимает около 45 Б на файл, на rb это 9 МБ на сессию. Если сессия упала без SessionEnd, её файлы лежат до 7 дней. При частых headless-запусках на большом репозитории это может дать сотни мегабайт в `.auto-context/state`. Можно сократить срок хранения для `.snapshot` (например, до 24 ч) или сжимать снимок: пути отсортированы, так что подойдёт кодирование общих префиксов.

## Что проверено и в порядке

- `Classify`, `UnitOf`, `excludedPath` и `skipDir` (с мемоизацией) — O(глубина пути). Квадратичного O(units × files) нет.
- `session.Diff` — O(N), 38 мс на 208k записей. `recordTurn` и `deletionTimes` кэшируют stat по каталогам.
- `parallelLstat` вызывает lstat только для «интересных» файлов: `.txt` и прочие не stat-ятся.
- Бюджет glob в `.gitignore`: doublestar не откатывается экспоненциально, 3e8 единиц бюджета — это ≤0,2 с.
- PreToolUse, PermissionRequest и SessionEnd стоят около 1 мс: `Open` и `Discover` они не вызывают.
- Шим `bin/auto-context` добавляет несколько fork (`uname`, `tr`, `dirname`), это ~3–5 мс.
- `Cache.Save` ничего не делает, если кэш чистый. `WriteState` пишет без fsync.
